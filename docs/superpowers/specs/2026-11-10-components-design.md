# Учёт компонентов и автоматическое применение эффектов

Дата: 2026-11-10. Дополняет и местами отменяет [спецификацию от 2026-11-05](2026-11-05-ti4-planner-design.md).

## 1. Что меняется в продукте

Раньше приложение считало только то, что игрок вносил записями, а способности, карты и технологии учитывались ручными
правками. Теперь приложение знает каждый компонент игры, знает, у кого он, и само применяет его эффект там, где это
возможно.

Решения пользователя от 2026-11-10:

- Автоматическое применение способностей, карт действий и технологий входит в продукт. Пункт «Не входит» старой
  спецификации об этом отменён.
- Тексты компонентов дословные, как на картах. Пересказы удаляются.
- Бой не считается. Боевые эффекты показываются подсказками в блоке боя, потери игрок по-прежнему вносит сам.
- Сохранения прежних версий не читаются: релиза не было.
- Владение показывается одной правой шторкой, как «Улучшения». Поиск компонента нечёткий.
- Вычисления оптимизируются, состояние экранов идёт через контроллер.

Что остаётся как было: предупреждения ничего не запрещают; ручная правка остаётся для случаев, которые правила не
покрывают; новые функции появляются в самом простом виде.

Не входит: симуляция боя, ветки планов, таблицы сравнения, синхронизация, арт, Twilight's Fall.

## 2. Части работы

Каждая часть получает свой план и оставляет приложение рабочим.

| № | Часть | Что даёт |
|---|---|---|
| 1 | Фундамент и данные | Контроллер состояния, новый формат сохранения, все компоненты с текстами, владение, движок эффектов, шторка «Компоненты» с поиском |
| 2 | Технологии | Что изучено, требования, лимиты, эффекты всех технологий |
| 3 | Фракции | Способности, лидеры, мехи, прорывы |
| 4 | Карты и планеты | Карты действий, реликвии, обязательства, исследование и прикрепления, легендарные планеты |
| 5 | Цели и законы | Очки от целей, фаза голосования, законы в силе, конец игры |

Параллельная линия: осмотр экранов и исправление найденных багов и неудобств, каждое с красным тестом до правки.

Этот документ подробно описывает часть 1 и задаёт контракты, на которые опираются части 2-5.

## 3. Данные

### 3.1. Компонент

```ts
type ComponentKind = 'technology' | 'actionCard' | 'relic' | 'publicObjective' | 'secretObjective' | 'agenda'
  | 'exploration' | 'promissory' | 'leader' | 'ability' | 'breakthrough' | 'mech' | 'legendary';

interface ComponentDef {
  id: string;            // уникален среди всех видов: '<kind>:<id источника>'
  kind: ComponentKind;
  name: string;          // английское название
  pack: 'base' | 'pok' | 'te';
  text: string;          // дословно с карты, абзацы через \n
  /** Сколько таких карт в колоде; для остального 1. */
  copies?: number;
  /** Фракция-владелец: фракционная технология, лидер, способность, прорыв, мех, обязательство. */
  faction?: string;
  /** Поля вида: фаза карты действия, этап цели и её очки, вид закона, черта исследования, тип лидера. */
  detail?: Record<string, string | number>;
}
```

Технологии, лидеры, мехи, прорывы и способности уже есть в пакетах (`TechDef`, `FactionSheet`). Они остаются там со
своими полями; `text` добавляется к ним, а каталог компонентов строится поверх: одна функция `componentsOf(pack)` даёт
плоский список `ComponentDef` всех видов. Отдельного хранения одного и того же в двух местах нет.

### 3.2. Сборка

`scripts/build-data.ts` дополнительно берёт из источника `action_cards`, `agendas`, `relics`, `explores`,
`attachments`, `promissory_notes`, `public_objectives`, `secret_objectives` и поля текста у технологий, лидеров,
способностей, прорывов, мехов и легендарных планет. В пакет попадает только официальное: base, PoK с Codex, Thunder's
Edge; прочие источники отбрасываются и записываются в `provenance.json` с причиной, как сейчас.

Тексты лежат в `src/data/texts/{base,pok,te}.json` (id компонента → текст), отдельно от чисел. Причины: числа под
лицензией проекта, а тексты карт принадлежат издателю; в каталоге лежит `NOTICE.md` с этим пояснением, и README
ссылается на него. Пакет загружается вместе с данными своего дополнения.

Русский текст: источника дословных русских формулировок нет, поэтому карточка показывает английский текст при любом
языке интерфейса. Поле `textRu` в формате предусмотрено и пустует.

Удаляются `techSummaries.ts`, `sheetSummaries.*`, `legendarySummaries.ts`, `shipSummaries.ts`, `cardSummaries.ts` и
всё, что их читает; на их место встаёт `text` компонента. Тексты стратегических карт берутся так же.

### 3.3. Проверка данных

Тесты сборщика (`scripts/*.test.ts`) проверяют: у каждого компонента непустой текст; id уникальны; каждая фракционная
ссылка ведёт на существующую фракцию; число карт действий, реликвий, целей и законов по дополнениям совпадает с
записанным в `docs/data-verification.md`.

## 4. Владение

### 4.1. Что хранится

Состояние партии по-прежнему не хранится, а вычисляется повтором записей. В `GameState` игрока появляется:

```ts
interface Holdings {
  /** Изученные технологии, включая улучшения юнитов. Заменяет GameState.upgrades. */
  technologies: string[];
  /** Карты действий на руке, с повторами. */
  hand: string[];
  relics: string[];
  /** Обязательства на руке и сыгранные перед собой. */
  promissory: string[];
  /** Лидеры: состояние по id. Отсутствующий закрыт. */
  leaders: Record<string, 'unlocked' | 'exhausted' | 'purged'>;
  breakthrough?: 'held' | 'exhausted';
  /** Выполненные цели. */
  scored: string[];
  /** Секретные цели на руке. */
  secrets: string[];
  /** Истощённые компоненты, которые готовятся в фазе статуса: технологии, реликвии, карты планет-легенд. */
  exhausted: string[];
}
```

Общее на партию, а не на игрока: `laws: string[]` (законы в силе), `revealed: string[]` (открытые общие цели),
`attachments: Record<planetId, string[]>`.

### 4.2. Откуда берётся

Исходное владение задаётся в `Game.start`: стартовые технологии фракции ставятся сами при старте партии, остальное
(то, что было у игроков к моменту, с которого начат план) отмечается в шторке. Дальше владение меняют записи:

- Каждая запись может нести `gains` и `spends`: списки id компонентов, которые игрок получил или потерял этой записью
  (взял карты действий, получил реликвию, отдал обязательство). Это общий механизм для всего, что не имеет своего поля.
- Карта Technology называет изученную технологию: `effects.researched` становится списком id вместо числа.
- Компонентное действие называет компонент: `{ type: 'component', componentId, choices }` вместо свободной заметки.
  Заметка остаётся для действий без компонента.
- Запись фазы статуса называет выполненные цели и взятые карты.
- Запись фазы голосования (новый тип `agenda`) называет закон и исход.

`GameState.upgrades` и `Game.upgrades` исчезают: улучшение юнита — это технология во владении.

### 4.3. Предупреждения владения

Новые коды, каждый через реестр правил: `componentNotHeld` (сыграно то, чего нет), `componentExhausted`,
`techPrerequisites`, `handOverLimit` (больше 7 карт действий в фазе статуса), `leaderLocked`. Части 2-5 добавляют свои.

## 5. Движок эффектов

### 5.1. Контракт

`src/domain/effects/`: один файл на компонент, собранные в реестр по id. Образец — обработчики карт стратегии
(`replay/cards/handler.ts`).

```ts
type EffectTier = 'passive' | 'play' | 'hint';

interface ComponentEffect {
  tier: EffectTier;
  /** Пункты LRR или номер карты, на которые опирается эффект. */
  rule: string;
  /** passive: поправки к шагам расчёта, пока компонент у игрока и готов. */
  modify?: Partial<Modifiers>;
  /** play: что происходит, когда компонент сыгран записью с выбором. */
  play?: (turn: EffectTurn) => void;
  /** hint: в каком блоке редактора показать напоминание. */
  hintAt?: RuleStep[];
}
```

`Modifiers` — именованные точки, в которые расчёт уже заходит: `speed(unit, ctx)`, `capacity`, `fleetLimit`,
`productionValue`, `unitCost`, `planetResources`, `planetInfluence`, `researchCost`, `prerequisites`, `tokensGained`,
`handLimit`, `vp`. Шаг расчёта спрашивает значение через одну функцию `applied(state, point, base, ctx)`, которая
проходит по готовым компонентам игрока. Шаг не знает ни одного компонента по имени.

Классы:

- `passive` — применяется само. Пример: +1 к значению полёта.
- `play` — применяется, когда игрок сыграл компонент записью и сделал выбор (цель, планета, число).
- `hint` — приложение ничего не считает и показывает текст компонента в блоке шага: всё боевое, реакции на чужие
  действия, эффекты с бросками.

Поправка от пассивного эффекта видна игроку: рядом с изменённым числом стоит название компонента (подпись в
`Popover`), чтобы автоматика не была чёрным ящиком.

### 5.2. Полнота

Контрактный тест `src/domain/effects/contract.test.ts` требует: у каждого компонента каталога есть запись в реестре
эффектов с классом и правилом; у каждого `passive` и `play` есть тест правила. В части 1 каждому компоненту
присваивается класс `hint` по умолчанию — приложение уже показывает его текст в нужном месте. Части 2-5 переводят
компоненты в `passive` и `play`, по одному файлу и одному тесту на компонент.

## 6. Контроллер состояния

### 6.1. Проблема

Сейчас каждый вопрос «состояние до записи», «после записи», «кто мешает маршруту» проигрывает план с начала, а экран
задаёт такие вопросы для каждой открытой записи. Хранилище смешивает документ партии, команды, историю отмены,
сохранение и ссылки.

### 6.2. Устройство

- `src/state/gameStore.ts` остаётся документом партии и командами. История отмены и очередь сохранения выносятся в
  свои модули (`history.ts`, `autosave.ts`).
- `src/domain/replay/timeline.ts`: один проход по плану даёт `Timeline` — состояние до и после каждой записи и
  предупреждения. Шаги расчёта перестают менять состояние на месте между записями: после каждой записи состояние
  замораживается снимком с общими неизменившимися частями (копируется только то, что запись тронула).
- Пересчёт с места правки: `Timeline` помнит записи по ссылке. При новом плане проход начинается с первой записи,
  которая изменилась по ссылке, от её сохранённого состояния «до». Правка карты, игроков или стартового владения
  сбрасывает всё.
- `src/state/projection.ts`: держит по одному `Timeline` на пару (план, режим «сейчас/прогноз») и отдаёт экранам
  готовое через хуки `useForecast()`, `useNow()`, `useStateBefore(id)`, `useStateAfter(id)`, `useBlockersBefore(id)`.
  `src/ui` больше не вызывает повтор напрямую; контрактный тест это проверяет.
- `stateBeforeEntry`, `stateAfterEntry`, `boardBeforeEntry`, `blockersBefore` остаются в домене тонкими функциями
  поверх `Timeline` для тестов правил.

### 6.3. Измерение

`src/domain/replay/timeline.bench.ts` (vitest bench): план из 6 раундов по 12 записей на 6 игроков. Замеряется полный
проход и правка последней записи, до и после переделки. Цифры записываются в план части 1; цель — правка последней
записи не дороже одной записи, а не всего плана.

## 7. Сохранения

`schemaVersion` начинается с 1 нового формата (поле `format: 'ti4-planner/2'`, чтобы старое сохранение нельзя было
принять за новое). Миграции из `src/storage/schema.ts` удаляются. Сохранение без этого поля стоит в списке как
непрочитанное с сообщением «Сохранено прежней версией приложения», его можно выгрузить или удалить — тот же путь, что
у битого сохранения. Ссылка на партию не меняется.

## 8. Интерфейс

### 8.1. Шторка «Компоненты»

Одна правая шторка, заменяет «Улучшения»; язычок показывает число компонентов игрока. Внутри:

- Сверху `PlayerChoice`: чьё владение показано (я или соперник).
- Поле поиска.
- Разделы `Section` по видам: технологии (с прежними карточками улучшений юнитов внутри), карты действий,
  реликвии, обязательства, лидеры, прорыв, цели, законы партии. Пустой раздел свёрнут в одну строку.
- Компонент — карточка: название, дополнение, полный текст по нажатию (`Popover`). Состояние цветом по правилам
  проекта: имеется — голубой край, истощён — приглушён. Снятие — `HexRemove` внутри карточки у правого края.
- То, что пришло из записи плана, подписано «с раунда N» и здесь не снимается, как сейчас у улучшений.

### 8.2. Поиск

Поле ищет по названию и тексту всех компонентов включённых дополнений. Найденное, чего у игрока нет, стоит ниже своего
с кнопкой добавления: так поиск служит и навигацией, и выбором. Тот же список с поиском (`ComponentPicker`) открывается
из редакторов: исследование, компонентное действие, `gains` записи.

Нечёткий поиск свой, в `src/domain/fuzzy.ts`, без зависимости: запрос делится на слова; слово совпадает с началом
слова названия, с подстрокой или с опечаткой в один символ на каждые четыре (расстояние редактирования); название
весит больше текста, начало слова больше середины. Ищет и по русской, и по английской раскладке одного и того же
набора клавиш. Индекс строится один раз на пакет.

### 8.3. Подсказки

Блок шага в редакторе (бой, высадка, производство, оплата, маршрут) показывает под собой компоненты класса `hint`,
которые есть у участников и относятся к этому шагу: название и текст по нажатию. В части 1 привязка компонента к шагу
берётся из данных источника там, где она есть (фаза карты действия, боевые модификаторы), остальное показывается только
в шторке.

## 9. Тесты

- Правила: по одному файлу LRR, как сейчас; `test.todo` о владении и компонентах превращаются в тесты по мере частей.
- Контракт: каждый компонент в реестре эффектов; `src/ui` не вызывает повтор и не создаёт предупреждений.
- Нечёткий поиск: опечатка, перестановка слов, раскладка, порядок выдачи.
- Timeline: результат полного прохода равен результату прохода с места правки на случайных планах.
- Сквозной: добавить технологию через поиск в шторке, увидеть её у игрока после перезагрузки.

## 10. Что часть 1 сознательно не делает

Эффекты конкретных компонентов (кроме улучшений юнитов, которые уже считаются и переезжают на движок), проверку
требований технологий, очки от целей, голосование. Это части 2-5; до них такой компонент виден, находится поиском,
отмечается во владении и показывает свой текст.
